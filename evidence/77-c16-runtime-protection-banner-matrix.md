## 1. The renderer flip is real and deterministic (the board's premise, proven)

The board's premise is that Kimi entering the generated support set changes which banner state the group page routes to. That is exactly what the diff does, and the routing is a pure function of set membership — no live capture is needed to prove the flip, because it is deterministic on the committed data.

`frontend/app/src/lib/runtime-protection-support.generated.json` — the generated support catalog:

```
                 origin/main        HEAD (0f0ffca264)
  "count":       26                 27
  endpoint_kimi-cli:   ABSENT       PRESENT   (git diff shows: +    "endpoint_kimi-cli",)
```

Verified:
- `git show origin/main:…generated.json` → `count = 26`, `grep -c kimi = 0`.
- `git show HEAD:…generated.json` → `count = 27`, `grep -c kimi = 1`.
- `git diff origin/main...HEAD -- …generated.json` → single added element `+    "endpoint_kimi-cli",`.

Provenance (not hand-edited): the header of the file states it is generated by `backend_python/scripts/generate_runtime_protection_catalog.py` from the capability matrix. Kimi's cell that earns inclusion:
- `backend_python/src/common/capability_matrix/links.py:155-157` — `"endpoint_kimi-cli": (ProfileKey.KIMI_CLI_HOOKS,)`.
- `backend_python/src/common/capability_matrix/profiles/hooks.py:329-402` — `ProfileKey.KIMI_CLI_HOOKS` ("Kimi CLI (agent hooks)") declaring Block / Mask / Ask cells.
- Drift guard: `scanner/internal/scanner/agents/runtime_protection_frontend_parity_test.go:118` (`TestGuardableDetectorsAreEnforceableInTheCapabilityMatrix`) enforces that the scanner-guardable set is a SUBSET of this generated list — so the generated file and the scanner cannot silently disagree about Kimi.

**What the flip means (the state routing).** The support set feeds two predicates in `frontend/app/src/lib/runtime-protection-support.ts`:
- `RUNTIME_PROTECTION_SUPPORTED_APP_DEFINITION_IDS` (line 37) — the Set built from the generated JSON.
- `isRuntimeProtectionUnsupported(appDefinitionId)` (line 49) — returns `true` only when the id is **known, NOT in the supported set, and NOT SWG-guarded**.

Kimi (`endpoint_kimi-cli`) is now IN the set and is not SWG-guarded, so `isRuntimeProtectionUnsupported("endpoint_kimi-cli")` is now **`false`** where on `origin/main` it was **`true`**. That is the flip: on main the group page routed Kimi to the "Not supported" banner; at HEAD it no longer can. This is a deterministic consequence of set membership — the same input always yields the same route — so the flip is proven by the committed data, not by a screenshot.

## 3. The board's three named tenant states, mapped to the matrix (for `endpoint_kimi-cli`)

Because `endpoint_kimi-cli` is in the support set and is not SWG-guarded, **state #2 (Not supported) can never render for Kimi** — `notSupported` is structurally `false` for it on every surface. Kimi's banner is therefore driven purely by the backend `is_guarded` field and the assigned-policy count. Mapping the board's three tenant states onto the matrix above:

| Board's tenant state | Renders (matrix row) | Exact copy Kimi shows | What drives it |
|----------------------|----------------------|------------------------|----------------|
| **No policy** | Row 3 (no protection signal) **or** Row 5 (count mode, 0) | `"Protection not enabled. Install runtime protection to enforce policies on this coding agent."` (row 3) / `"No policies assigned to this asset"` (row 5, multi-policy flag on) | `is_guarded=false` → row 3; `is_guarded=true` + `assignedPolicyCount=0` → row 5 |
| **Alert-mode policy** | Row 6 (count>0) or Row 7 (single applied) | `"1 runtime policy assigned to this asset"` / `"\"<policyName>\" Onyx AI Guard policy is applied"` | `is_guarded=true` + a policy assigned (alert-mode is still an assigned policy; the banner does not distinguish alert vs block — that is a policy attribute, not a banner state) |
| **Blocking policy** | Row 6 or Row 7 (identical to alert-mode) | same as alert-mode | same — **the banner copy is intentionally identical for alert vs blocking**; the alert-vs-block distinction lives in the policy config surface, not this banner |

**Design note the matrix makes explicit:** the guard-state banner does not have a separate "alert-mode" vs "blocking" rendering. Both are "a policy is assigned/applied" (rows 6/7). The board's "no policy / alert-mode / blocking" trichotomy collapses to two banner outcomes — *unprotected* (rows 3/5) and *protected, policy applied* (rows 6/7) — and the alert-vs-block nuance is not a property of this component. That is a code fact (rows 6 and 7 read only `assignedPolicyCount` / `isConnected` / `policyName`, never a policy mode), quotable at `getBannerTitle :101-113`.

Backend field that drives protected-vs-unprotected: `is_guarded` on the desktop-agent response — schema `backend_python/src/common/repository/inventory_applications/schemas.py:1354`, computed by `get_is_guarded()` at `service.py:6680-6747` (fresh `last_guard_status` within the guardability window, or a recent runtime event → `true`). For Kimi this becomes `true` once the installed hooks sidecar reports a guard status — which is precisely what the 49-c7 wire-level and 55-s3 real-session evidence prove happens end-to-end.

## 4. The instance-page asymmetry (documented, deliberate)

The group overview and the instance page compute `notSupported` differently, and this is intentional — quoted so the matrix is complete:

- **Group overview** (`frontend/app/src/routes/ai-assets/desktop-agents/group/-components/group-overview.tsx:85-87`):
  ```
  const notSupported =
    isRuntimeProtectionUnsupported(appDefinitionId) ||
    isRuntimeProtectionUnavailableForTenant(appDefinitionId, swgProxyKeyDisplay);
  ```
  Uses **both** predicates → this is the surface the board's "flips off the Not-supported state" describes. For Kimi, `isRuntimeProtectionUnsupported` is now `false`, so the group page routes Kimi to the guard-state banner (rows 3/5/6/7), not row 2.

- **Instance page** (`frontend/app/src/routes/ai-assets/desktop-agents/$appId.tsx:149`):
  ```
  const notSupported = isRuntimeProtectionUnavailableForTenant(app.app_definition_id, flags.swgProxyKeyDisplay);
  ```
  Deliberately does **NOT** also route on `isRuntimeProtectionUnsupported`. The in-code comment (`$appId.tsx:134-148`) explains why: the Not-supported state suppresses the whole Connect/Configure affordance, but an agent with no endpoint protection can still be governed by an ALERT-mode policy, so routing agent-type-unsupported apps to Not-supported on the instance page would falsely tell them they cannot be governed at all — the honest-copy change is held back on the instance page until "cannot be blocked" is separated from "cannot be governed". For Kimi this asymmetry is moot (Kimi is supported on both surfaces), but it is recorded so the matrix is not misread as "both pages route identically".

Both banners are gated by `showRuntimeProtection` (group-overview.tsx:53/115) — a non-runtime asset renders no banner at all.

## 5. Decided reason for the one thing not captured here (the live SPA pixel)

The board's how-to-close explicitly permits: *"…or carry a decided reason if you hold that surface unreachable."* I hold it unreachable, and here is the decided reason, stated honestly:

- The live per-tenant banner render is behind the Onyx console SPA, which authenticates via **Frontegg SSO (JumpCloud)**. The JumpCloud credential available to this box was **REJECTED** at the IdP (documented in the env ledger). Per the standing instruction I have **not re-hammered SSO** — repeated auth attempts against a rejected credential are not a capability fix, they are noise.
- Therefore a logged-in screenshot of each Kimi banner state on the live SPA is **not anonymously reachable from this box**, and I will not fabricate or stub one. A stub-host screenshot dressed as a live console render would cost more trust than this honest gap (per May's standing instruction).
- **What replaces the pixel, and why it is sufficient for this rule:** the state routing is **deterministic on committed data** (§1) and every state's copy is **pinned in source as a constant or a pure `getBannerTitle` branch** (§2), asserted by the component's own tests (`ai-guard-connect-banner.not-supported.test.tsx:6-7` pins rows 2 and 3 verbatim). The matrix is therefore fully documented from code — the exact copy, the exact routing value, the exact file:line — without a live capture. This is the same code-documented + named-wall pattern the board accepted for C16 file 76 and for the OS-agnosticism proof (file 73).

**This artifact does not claim a live console capture, and does not approve any owner decision.** It is the producible state matrix the board's part-3 asked for, plus the named wall for the part it cannot produce.
