## Honest disclosure (nothing dressed up)
- **This lane has no pod in kind-slate** (only endpoint-swg-ingestion is deployed as a pod), so the
  handler is run here via `uv run --no-sync python` against the SAME branch code + the SAME real
  localstack queues/S3 + real Postgres the deployed lane would use. The poison→DLQ path exercised is
  byte-identical to the deployed code (message_handler.py `_park_poison` → sqs.py `dead_letter_message`).
- **`flag_key=None` on the processor** isolates the poison path. The per-tenant LaunchDarkly lane-gate
  is UPSTREAM of and ORTHOGONAL to the poison mechanism: it only decides ack-drop vs proceed and can
  never itself park. Wiring LaunchDarkly into this local harness is not the thing under test; the
  poison-park mechanism is. (The one `Feature flag service not initialized, returning default` line is
  the benign subagents-flag default with raise_on_error=False — expected in this local context.)
- **Counters read `nan`** because this isolated one-shot process has no prometheus multiprocess
  registry scraped — the increment call sites (`metrics.poison_messages.inc(...)` /
  `metrics.dead_letters.inc()`) do run, but their value is not observable from this harness. The DLQ
  message itself + the two consumer log lines ("dead-lettering" / "Moved message to DLQ") ARE the
  proof; the counter read is reported honestly as unobserved rather than faked.
- **localstack endpoint** is `http://127.0.0.1:4599` (a fresh port-forward to svc/localstack:4566);
  used instead of the IPv6 `[::1]:4566` pf because S3Config's endpoint validator accepts `127.0.0.1`
  but not `[::1]`. Same localstack, same queues.

The harness that produced this: /tmp/c11_dlq_harness.py (real clients only — no mock/stub anywhere).
